# Project Rules

## Windmill Development

### Creating a new script

1. Write `f/<area>/<name>.py` with a `main` function. Add the module
   header `# requirements: project` (or a named requirements set).
2. Run `wmill generate-metadata --workspace localdev --yes` to produce
   the matching `.script.yaml` and `.script.lock`. Do not hand-write
   `.script.yaml` — the auto-generated style uses `originalType`,
   `default: null`, and `format: resource-*` markers that hand-written
   YAML misses.
3. Add a `summary` and `description` to the generated `.script.yaml`.
   Leave `schema` / `required` as-is.
4. Run `pixi run check` and address anything on the files you touched.
5. Run `pixi run dev-run f/<area>/<name>` (no `.py` ext), appending
   `--args <JSON args>` if the script requires arguments.

### Editing an existing script

1. Edit the `.py` only.
2. Run `wmill generate-metadata --workspace localdev --yes` (regenerates
   `.script.yaml` and `.script.lock`).
3. Run `pixi run check` and `pixi run dev-run` to verify.

### Adding a new dependency

1. Add the package to `pyproject.toml` `[project].dependencies`.
2. Run `pixi install` (updates `pixi.lock`).
3. Run `pixi run deps` (regenerates `dependencies/*.requirements.in` and
   `uv.lock`).
4. Run `wmill generate-metadata --workspace localdev --yes` for any
   script that imports it (adds the package to `.script.lock`).
5. Run `wmill sync push` (refreshes `wmill-lock.yaml` hashes).

If a diff shows up in one of the auto-generated files below, your work
is incomplete — run the matching generator and re-stage. Do not commit
manual edits to those files.

### Auto-Generated Files

- `f/graphql/api_client/*` &mdash; run `pixi run graphql`
- `f/graphql/schema.gql` &mdash; run `pixi run graphql`
- `**/*.script.yaml` &mdash; run `wmill generate-metadata --workspace localdev --yes`
- `**/*.script.lock` &mdash; run `wmill generate-metadata --workspace localdev --yes`
- `**/*.inline_script.lock` &mdash; run `wmill generate-metadata --workspace localdev --yes`
- `**/*.flow/**/flow.yaml` &mdash; run `wmill generate-metadata --workspace localdev --yes`
- `dependencies/*.requirements.in` &mdash; run `pixi run deps`
- `wmill-lock.yaml` &mdash; regenerated by `wmill sync push`
- `pixi.lock` &mdash; run `pixi install`
- `uv.lock` &mdash; regenerated by `pixi run deps`

## Survey existing patterns first

Before designing a new script or flow, search `f/` for adjacent work:
look at folders with similar scope, grep for the operation you're
implementing (e.g. `add_items`, `apply_associations`, `entity_context`),
and read the dispatcher module in that area before writing from scratch.
If a flow or dispatcher already covers the use case, decide whether to
extend it or add a new module only after reading the existing one.

## Pre-commit discipline

- `pixi run check` runs `ruff check --fix && ruff format && npx oxfmt
&& basedpyright`. The pre-commit hook (`pixi run prek`) re-runs ruff.
- The project ruff config keeps trailing commas (e.g. `**kwargs,`).
  Do not strip them by hand in generated files.
- If a hook reformats a file during `git commit`, the commit aborts.
  Re-stage (`git add <file>`) and retry — do not use `--no-verify`.
- `basedpyright` may not resolve packages installed by pixi without
  `--pythonpath .pixi/envs/default/bin/python`. A `reportMissingImports`
  error on a package listed in `pyproject.toml` is a tooling artifact,
  not a real code issue.

## Important Tips

- Only top level folders under `f/` can have `folder.meta.yaml` files.
  Subfolders can be created but do not include a `folder.meta.yaml` file.
- Non-source files (`.tsv`, `.json`, `.txt`, `.jinja`, etc.) should only
  be created under the `src/` hierarchy. If you reference one of these
  files in a script/flow under `f/`, you must use `checkout_repo()`
  within the script and access it under `databot/src/` in the worker
  environment.

## Script Writing Principles

- Scripts must export a `main` function (do not call it)
- Libraries are installed automatically — do not show installation instructions
- Credentials and configuration are stored in resources and passed as parameters
- Scripts can return any JSON-serializable value; return values are
  available to subsequent flow steps via `results.step_id`
- Preprocessor scripts are named `preprocessor` and receive a single
  `event` parameter

## Flow Guidance

When asked to create a flow, create a new folder ending with `.flow`
containing a `.yaml` file with the flow definition.

For `rawscript` type modules, the `content` key should start with
`!inline` followed by the path of the script. For `script` type
modules, `path` should be the full repository path.

After creating/modifying flows, run `wmill generate-metadata
--workspace localdev --yes` to regenerate script YAML and locks.
